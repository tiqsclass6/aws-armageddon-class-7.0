## 1. Executive Summary

A deliberate credential mismatch was introduced between the **RDS MySQL instance** and the value stored in **AWS Secrets Manager**. This resulted in complete loss of application functionality. The Flask application running on the **EC2 instance** was unable to authenticate to the database, causing all **API endpoints (`/init`, `/add`, `/list`)** to return **HTTP 500 Internal Server Error** responses.

The incident was detected promptly through the pre-configured **CloudWatch** monitoring and alerting pipeline. Structured diagnosis, containment, and recovery were completed within approximately 12 minutes with no permanent data loss or infrastructure damage.

---

## 2. Affected Components

- **EC2 Instance** — Flask application host  
- **RDS Instance** — MySQL database (identifier: `lab-1c-mysql_v15`)  
- **Secrets Manager Secret** — `lab/rds/mysql_v15` (used by the application for credential retrieval)  

---

## 3. Impact

- **Severity** — High (complete loss of application write/read functionality)  
- **Scope** — All database-dependent API operations were unavailable  
- **Business Impact** — No new notes could be added or retrieved during the incident period  
- **Duration** — Approximately 10–15 minutes from introduction of the failure to full restoration  

---

## 4. Detection

The failure was identified through the following mechanisms:

**Primary Detection**  

- CloudWatch Alarm `lab-1c-db-connection-failure` triggered after the custom metric `DBConnectionErrors` (generated by the log metric filter) exceeded the threshold of 3 failures within a 5-minute evaluation period.

**Notification**  

- Delivered an email alert to the configured SNS email subscription.

**Secondary Confirmation**  

- Manual testing of application endpoints returned HTTP 500 Internal Server Error responses.

**Log Analysis**  

- CloudWatch Logs filter (searching for "Access denied for user") revealed repeated `pymysql.err.OperationalError` exceptions with messages indicating authentication failure.

---

## 5. Root Cause Analysis

**Root Cause**  
Credential mismatch (drift) between the **RDS DB instance master password** and the value stored in **AWS Secrets Manager**.

> [!NOTE]
> The RDS master password was intentionally modified to an incorrect value as part of the incident simulation exercise. The **Flask** application continued to retrieve and use the original (now invalid) password from the Secrets Manager secret `lab/rds/mysql_v15`. This resulted in repeated authentication failures during database connection attempts, manifesting as `pymysql.err.OperationalError` exceptions with "Access denied for user" messages.

**Contributing Factors**  

- No automated credential synchronization or validation mechanism was in place between Secrets Manager and the RDS instance (as designed for this lab exercise).  
- The application did not implement fallback or retry logic for credential validation prior to full operation.

## 6. Timeline & Time to Recovery

**Total Time to Recovery**  
Approximately 12 minutes from detection to full restoration.

**Detailed Breakdown**  

- Time from first failed request to alarm trigger: **~5–7** minutes (alarm evaluation period)  
- Time to acknowledge and diagnose via logs and configuration validation: **3 minutes**  
- Time to retrieve correct password from **Secrets Manager** and apply it to RDS: **2 minutes**  
- Time for Secrets Manager password change to propagate and instance to return to "available" status: **2–3 minutes**  
- Final verification (successful `/list` endpoint response): immediate after recovery

---

## 7. Recovery Actions Performed

1. Retrieved the correct master password from **Secrets Manager** using the AWS CLI.  
2. Restored the RDS master password to match the existing Secrets Manager value.
3. Monitored RDS instance status until it returned to "available".  
4. Validated application functionality by successfully executing endpoints `/init`, `/add`, and `/list`.  
5. Confirmed alarm clearance and absence of new error events in **CloudWatch Logs** in the subsequent 5-minute period.

---

## 8. Post-Incident Validation

- All application endpoints returned successful responses.  
- **CloudWatch Alarm** state returned to `OK`.  
- No new error events appeared in the CloudWatch Logs group `/aws/ec2/lab-1c-rds-app` in the subsequent 5-minute period.

---

## 9. Lessons Learned & Recommendations

- **Credential Consistency**  
  Implement automated validation or synchronization between **Secrets Manager** and RDS to prevent drift in production environments.

- **Monitoring Effectiveness**  
  The **CloudWatch Logs metric filter, alarm, and SNS notification** pipeline proved highly effective for early detection.

- **Logging Quality**  
  Application logging (via `watchtower`) provided critical diagnostic information.

- **Runbook Discipline**  
  Strict adherence to the structured incident response runbook minimized recovery time and preserved system state.
